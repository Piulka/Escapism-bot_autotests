# QA findings

Живой backlog дефектов и улучшений, найденных при исследовании Escapism и
разработке автотестов.

Статусы: `New`, `Confirmed`, `In progress`, `Fixed`, `Won't fix`.
Приоритеты: `P0` — блокирует критичный путь, `P1` — значимый риск,
`P2` — заметная проблема, `P3` — улучшение.

## API и инфраструктура

### API-001 — Периодические продолжительные ответы 502

- Тип: bug / test environment stability
- Приоритет: P1
- Статус: Confirmed
- Затронуто: `GET /api/v1/profile`, `GET /api/guild`,
  `GET /api/guild/members`, `GET /api/guild/applications`,
  `POST /api/v1/account/reset`, `POST /api/guild/leave`,
  `POST /api/warehouse/withdraw`
- Наблюдение: endpoint может возвращать `502 Bad Gateway` несколько раз подряд
  после успешной UI-операции или во время setup/cleanup. В UI это также
  воспроизводится экраном `Не удалось загрузить данные → Повторить` при открытии
  каталога гильдий сразу после успешного создания.
- Влияние: корректный пользовательский сценарий становится красным из-за
  недоступности setup, проверки или teardown. Один `502` от account reset
  блокирует все зависящие от fixture тесты, а ошибка guild cleanup оставляет
  состояние, влияющее на последующие экраны.
- Автотесты: retry и best-effort cleanup не используются — любой `502` остаётся
  видимым падением с endpoint, статусом и телом ответа.
- Ожидание: найти причину gateway errors и обеспечить стабильный test API.

### API-002 — Account reset не очищает связанные состояния

- Тип: testability improvement
- Приоритет: P2
- Статус: Confirmed
- Затронуто: guild membership и личный warehouse.
- Наблюдение: `POST /api/v1/account/reset` возвращает базовый inventory/profile,
  но может оставить гильдию и содержимое личного склада.
- Влияние: тесты вынуждены иметь отдельный cleanup и восстанавливать дельты.
- Дополнительное влияние: после неуспешного guild cleanup обычный account reset
  сохраняет membership. В результате независимый inventory-тест получает другое
  состояние UI (`Переместить` вместо `На склад`) и корректно падает на нарушенной
  предусловии.
- Ожидание: документировать контракт reset либо добавить полный test reset с
  очисткой guild/mail/warehouse и других связанных сущностей.

### API-003 — Контракт exchange изменился без актуальной документации

- Тип: documentation defect
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: webapp начал передавать `minAmountOut`, но поле отсутствовало в
  описании `POST /api/exchange`.
- Влияние: контрактный assertion smoke-теста обнаружил незадокументированное
  изменение.
- Workaround: локальная `API_REFERENCE.md` дополнена полем.

## UX/UI и accessibility

### UI-001 — У кнопки фильтров инвентаря нет доступного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: button содержит только `svg.lucide-funnel`, без `aria-label` и
  видимого текста.
- Влияние: screen reader не объясняет действие; тест использует CSS-класс иконки.
- Ожидание: добавить `aria-label="Фильтры"`.

### UI-002 — Equipment slots не имеют стабильных locator

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: все 8 equipment slots реализованы как кликабельные `div` без
  `role`, `aria-label` и `data-testid`; smoke-тест временно использует
  `locator("svg").nth(3)` для слота головы.
- Влияние: изменение порядка SVG может сломать тест без изменения функции.
- Ожидание: accessible button name или `data-testid` с ключом equipment slot.

### UI-003 — Строка участника гильдии не является доступной кнопкой

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: управление участником открывается кликом по тексту ника; button role
  и доступное имя отсутствуют.
- Ожидание: использовать `<button>` либо добавить корректные role, keyboard
  interaction и accessible name.

### UI-004 — Карточки выбора почтовых вложений не имеют стабильного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: элементы временно выбираются по позиции `div.aspect-square`.
- Дополнительное наблюдение: кнопки удаления уже прикреплённых предметов также
  не имеют accessible name и определяются по `svg.lucide-trash2`.
- Влияние: сортировка inventory способна выбрать другое вложение.
- Ожидание: accessible name с названием предмета и количеством либо test id с
  item ID; для удаления — имя вида `Удалить вложение: Морковь`.

### UI-005 — Unread-индикатор письма не имеет семантического состояния

- Тип: accessibility / testability
- Приоритет: P3
- Статус: Confirmed
- Наблюдение: состояние проверяется по CSS-классу.
- Ожидание: добавить текст для screen reader, `aria-label` или `data-testid` с
  явным read/unread state.

### UI-006 — Кнопка направления обмена не имеет доступного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: locator строится по `svg.lucide-arrow-down-up`.
- Ожидание: динамический `aria-label`, например `Обменять золото на серебро`.

### UI-007 — Крестик карточки предмета не имеет доступного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: основной item dialog содержит первым элементом button только с
  иконкой закрытия; доступное имя отсутствует.
- Влияние: screen reader не объясняет действие, а тест вынужден выбирать первую
  кнопку внутри dialog.
- Ожидание: добавить `aria-label="Закрыть карточку предмета"`.

### UI-008 — Заблокированные действия предмета теряют назначение

- Тип: UX / accessibility
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: после lock четыре разных действия получают одинаковое accessible
  name `Заблокировано`.
- Влияние: пользователь screen reader не может определить, какое действие было
  запрещено; сообщения теста также теряют контекст.
- Ожидание: сохранить название действия и объяснить причину, например
  `Надеть — недоступно: предмет заблокирован`.

### UI-009 — Выброс предмета выполняется без подтверждения

- Тип: UX / destructive action
- Приоритет: P1
- Статус: Confirmed
- Наблюдение: нажатие `Выбр.` в карточке предмета сразу отправляет
  `POST /api/inventory/trash`; диалог подтверждения отсутствует. На viewport
  VK Mini App название действия также сокращено до неочевидного `Выбр.`.
- Влияние: пользователь может безвозвратно удалить предмет случайным нажатием и
  не получает возможности проверить выбранный предмет перед операцией.
- Ожидание: показывать подтверждение с названием предмета и явными действиями
  `Отмена` / `Выбросить`; использовать полное доступное имя кнопки даже при
  визуально сокращённой подписи.
- Автотест: ожидаемый confirmation-flow описан как `xfail(strict=True)`. После
  исправления XPASS намеренно сделает прогон красным, пока отметка известного
  дефекта не будет снята.

### UI-010 — Информационные контролы биржи не имеют доступных имён

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: кнопка открытия информации определяется только по
  `svg.lucide-info`, а кнопка закрытия внутри `dialog "О Бирже валюты"` не имеет
  accessible name.
- Влияние: назначение кнопок не объявляется screen reader; UI-тест зависит от
  реализации иконок.
- Ожидание: добавить доступные имена `О Бирже валюты` и `Закрыть информацию о
  Бирже`.

### UI-011 — После отклонения нельзя повторно подать заявку в гильдию

- Тип: functional bug
- Приоритет: P1
- Статус: Confirmed
- Наблюдение: лидер успешно отклоняет заявку, `POST
  /api/guild/applications/{id}/reject` возвращает `200`, а последующий `GET
  /api/guild/applications` возвращает пустой список. Однако после повторного
  открытия каталога у кандидата не появляется кнопка `Подать заявку`: карточка
  продолжает отображать заявку как уже поданную.
- Влияние: пользователь не может повторно подать заявку после отклонения, хотя
  сервер больше не считает её активной.
- Ожидание: после успешного reject обновлять состояние каталога и разрешать новую
  заявку этому пользователю.
- Автотест: полный ожидаемый flow `reject → reapply → accept → leave` сохранён как
  `xfail(strict=True)`. Исправление даст `XPASS(strict)` до снятия отметки.

### UI-012 — UI ограничивает текст набора 250 символами вместо 500

- Тип: functional / contract mismatch
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: `API_REFERENCE.md` и backend-контракт допускают текст набора до 500
  символов, но textarea формы имеет `maxlength="250"` и обрезает остаток.
- Влияние: валидный по API текст невозможно ввести через пользовательский UI.
- Ожидание: привести UI к документированному лимиту 500 либо согласованно изменить
  контракт и документацию, если продуктовый лимит должен быть равен 250.
- Автотест: документированный лимит зафиксирован как `xfail(strict=True)`.

### UI-013 — Кнопка редактирования текста набора не имеет доступного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Confirmed
- Наблюдение: button содержит только `svg.lucide-pen`, без `aria-label`, видимого
  текста и test id.
- Влияние: screen reader не сообщает назначение кнопки; тест зависит от класса
  иконки.
- Ожидание: добавить `aria-label="Редактировать текст набора"`.

### UI-014 — Обычный участник видит редактирование текста набора

- Тип: authorization UX / functional bug
- Приоритет: P1
- Статус: Confirmed
- Наблюдение: у пользователя с `myRole="member"` отображается кнопка с
  `svg.lucide-pen`, открывающая форму редактирования публичного текста набора.
  По API-документации операция разрешена только лидеру.
- Влияние: UI предлагает участнику запрещённое действие; фактическая защита
  зависит только от backend.
- Ожидание: не отображать контрол редактирования для member. Backend-проверку
  прав сохранить независимо от UI.
- Автотест: ожидаемое отсутствие кнопки отмечено `xfail(strict=True)`; прямой
  API-запрет проверяется отдельным проходящим тестом.

### UI-015 — Карточка перекрывает кнопку details технологии

- Тип: layout / functional bug
- Приоритет: P1
- Статус: Confirmed
- Наблюдение: на экране технологий кнопка `Детали` видима и enabled, но pointer
  events перехватывает родительский кликабельный контейнер карточки. Обычный click
  не достигает кнопки.
- Влияние: пользователь не может открыть подробности технологии штатным способом.
- Ожидание: исправить слои/обработчики карточки, чтобы вложенная кнопка была
  кликабельна без force-click и всплытие события обрабатывалось корректно.
- Автотест: ожидаемое открытие details-dialog сохранено как `xfail(strict=True)`.

## Правила добавления findings

- Не записывать предположение как подтверждённый bug.
- Для воспроизводимого дефекта указывать экран, действие, фактический и ожидаемый
  результат.
- Проблемы тестового стенда отделять от продуктовых дефектов.
- После исправления сохранять запись и менять статус на `Fixed` с версией/датой.
