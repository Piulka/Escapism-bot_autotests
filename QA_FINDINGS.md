# QA findings

Живой backlog дефектов и улучшений, найденных при исследовании Escapism и
разработке автотестов.

Статусы: `New`, `Confirmed`, `In progress`, `Fixed`, `Won't fix`.
Приоритеты: `P0` — блокирует критичный путь, `P1` — значимый риск,
`P2` — заметная проблема, `P3` — улучшение.

## API и инфраструктура

### API-001 — Периодические продолжительные ответы 502

- Тип: bug / test environment stability
- Приоритет: P1
- Статус: Confirmed (повторно воспроизведено 2026-08-21)
- Затронуто: `GET /api/v1/profile`, `GET /api/guild`,
  `GET /api/guild/members`, `GET /api/guild/applications`,
  `POST /api/v1/account/reset`, `POST /api/guild/leave`,
  `POST /api/warehouse/withdraw`
- Наблюдение: endpoint может возвращать `502 Bad Gateway` несколько раз подряд
  после успешной UI-операции или во время setup/cleanup. В UI это также
  воспроизводится экраном `Не удалось загрузить данные → Повторить` при открытии
  каталога гильдий сразу после успешного создания.
- Влияние: корректный пользовательский сценарий становится красным из-за
  недоступности setup, проверки или teardown. Один `502` от account reset
  блокирует все зависящие от fixture тесты, а ошибка guild cleanup оставляет
  состояние, влияющее на последующие экраны.
- Автотесты: retry и best-effort cleanup не используются — любой `502` остаётся
  видимым падением с endpoint, статусом и телом ответа.
- Ожидание: найти причину gateway errors и обеспечить стабильный test API.
- Результат расследования: процесс PHP 8.6 падал с `SEGV/ABRT` при сочетании
  TrueAsync и `opcache.jit=tracing`. После `opcache.jit=disable` повторные
  точечные проверки прошли, но полный последовательный E2E-прогон снова получил
  502 на `GET /api/v1/profile`. Retry в тесты не добавлялся.

### API-002 — Account reset не очищает связанные состояния

- Тип: documented limitation / testability improvement
- Приоритет: P2
- Статус: Confirmed
- Затронуто: guild membership, guild bank и mail.
- Наблюдение: актуальный `API_REFERENCE.md` явно исключает guild membership,
  guild bank и mail из reset. Личный warehouse, наоборот, входит в контракт очистки.
- Влияние: тесты вынуждены иметь отдельный cleanup и восстанавливать дельты.
- Дополнительное влияние: после неуспешного guild cleanup обычный account reset
  сохраняет membership. В результате независимый inventory-тест получает другое
  состояние UI (`Переместить` вместо `На склад`) и корректно падает на нарушенной
  предусловии.
- Ожидание: тесты выполняют отдельный cleanup guild/mail; полный test reset был бы
  полезен, но отсутствие этой очистки больше не считается недокументированным bug.

### API-003 — Контракт exchange изменился без актуальной документации

- Тип: documentation defect
- Приоритет: P2
- Статус: Fixed (документация актуализирована 2026-08-21)
- Наблюдение: webapp начал передавать `minAmountOut`, но поле отсутствовало в
  описании `POST /api/exchange`.
- Влияние: контрактный assertion smoke-теста обнаружил незадокументированное
  изменение.
- Проверка фикса: документация описывает `minAmountOut`, минимум 100,
  целочисленную комиссию `ceil(5%)` и реинвестирование `fee // 2`; формулы тестов
  приведены к опубликованному контракту.

### API-004 — Account reset возвращает 500 во время деградации стенда

- Тип: bug / test environment stability
- Приоритет: P1
- Статус: Confirmed (повторно воспроизведено 2026-08-21)
- Наблюдение 2026-08-21: помимо периодических `502`, `POST
  /api/v1/account/reset` несколько раз вернул `500 Internal Server Error` с
  телом `{"error":"Internal Server Error","code":"INTERNAL_ERROR"}`.
- Влияние: fixture не может создать известное начальное состояние; зависимые
  тесты корректно останавливаются на setup.
- Ожидание: reset тестового пользователя должен быть транзакционным и стабильно
  возвращать 200 либо диагностируемую доменную ошибку, а не generic 500.
- Проверка: отдельный контрактный reset-тест прошёл, но в полном последовательном
  прогоне `POST /api/v1/account/reset` снова вернул generic 500. Серверное
  логирование Throwable должно дать точную причину этого запроса.

### API-005 — Account reset очищает почту вопреки актуальной документации

- Тип: API contract / documentation defect
- Приоритет: P1
- Статус: Confirmed (2026-08-21)
- Документация: `API_REFERENCE.md` прямо указывает, что `mails` не сбрасываются.
- Факт: письмо с уникальной темой было создано через `POST /api/mail/send`, найдено
  у получателя, после `POST /api/v1/account/reset` исчезло; вместо состояния до
  reset backend восстановил seed-набор почты.
- Влияние: клиент и автотесты не могут полагаться на опубликованные границы reset;
  reset способен удалить пользовательскую почту.
- Ожидание: либо перестать очищать почту, либо явно включить `clearMails/seedMails`
  в контракт endpoint.
- Автотест: ожидаемое сохранение уникального письма закреплено как
  `xfail(strict=True)` без retry и обходов.

## UX/UI и accessibility

### UI-001 — У кнопки фильтров инвентаря нет доступного имени

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Fixed (проверено 2026-08-21)
- Наблюдение: button содержит только `svg.lucide-funnel`, без `aria-label` и

- Проверка фикса: regression-тест использует role/name `Фильтры` без CSS-иконки.

### UI-002 — Equipment slots не имеют стабильных locator

- Тип: accessibility / testability
- Приоритет: P2
- Статус: Fixed (основной accessibility-контракт, проверено 2026-08-21)
- Наблюдение: все 8 equipment slots реализованы как кликабельные `div` без
  `role`, `aria-label` и `data-testid`; smoke-тест временно использует
  `locator("svg").nth(3)` для слота головы.
- Влияние: изменение порядка SVG может сломать тест без изменения функции.
- Ожидание: accessible button name или `data-testid` с ключом equipment slot.
- Проверка фикса: slot получил role, keyboard semantics, aria-label и test id.
  Дублирование test id в responsive DOM вынесено отдельно как UI-016.

### UI-008 — Заблокированные действия предмета теряют назначение

- Тип: UX / accessibility
- Приоритет: P2
- Статус: Fixed (проверено автотестом 2026-08-21)
- Наблюдение после частичного фикса 2026-08-21: `На склад — заблокировано` и
  `Разобрать — заблокировано` различимы, `Выбросить предмет` сохраняет назначение,
  но действие экипировки всё ещё называется только `Заблокировано`.
- Влияние: пользователь screen reader не может определить, какое действие было
  запрещено; сообщения теста также теряют контекст.
- Ожидание: сохранить название действия и объяснить причину, например
  `Надеть — недоступно: предмет заблокирован`.
- Проверка фикса: `Надеть — заблокировано` и остальные имена проверяются без
  xfail; сценарий lock/unlock проходит.

### UI-009 — Выброс предмета выполняется без подтверждения

- Тип: UX / destructive action
- Приоритет: P1
- Статус: Fixed (проверено 2026-08-21)
- Наблюдение: нажатие `Выбр.` в карточке предмета сразу отправляет
  `POST /api/inventory/trash`; диалог подтверждения отсутствует. На viewport
  VK Mini App название действия также сокращено до неочевидного `Выбр.`.
- Влияние: пользователь может безвозвратно удалить предмет случайным нажатием и
  не получает возможности проверить выбранный предмет перед операцией.
- Ожидание: показывать подтверждение с названием предмета и явными действиями
  `Отмена` / `Выбросить`; использовать полное доступное имя кнопки даже при
  визуально сокращённой подписи.
- Проверка фикса: confirmation-flow проходит без xfail; диалог содержит имя
  предмета, а `POST /api/inventory/trash` отправляется после подтверждения.

### UI-011 — После повторной подачи список заявок не согласован с badge

- Тип: functional bug
- Приоритет: P1
- Статус: Confirmed (частичный фикс проверен 2026-08-21)
- Наблюдение: лидер успешно отклоняет заявку, `POST
  /api/guild/applications/{id}/reject` возвращает `200`, а последующий `GET
  /api/guild/applications` возвращает пустой список. Однако после повторного
  открытия каталога у кандидата не появляется кнопка `Подать заявку`: карточка
  продолжает отображать заявку как уже поданную.
- Влияние: пользователь не может повторно подать заявку после отклонения, хотя
  сервер больше не считает её активной.
- Ожидание: после успешного reject обновлять состояние каталога и разрешать новую
  заявку этому пользователю.
- Повторная подача после reject теперь доступна. После неё API содержит заявку и
  badge лидера показывает `Заявки (1)`, но открытый список сообщает «Заявок не
  найдено». Полный flow оставлен `xfail(strict=True)` без reload/retry.
- Перепроверка 2026-08-21: USER_2 вернулся на главный экран и заново открыл
  раздел гильдий, чтобы гарантированно вызвать `refetchOnMount`; кнопка повторной
  подачи всё равно не появилась. На текущем deployment фикс не подтверждён.

### UI-012 — UI ограничивает текст набора 250 символами вместо 500

- Тип: functional / contract mismatch
- Приоритет: P2
- Статус: Fixed (проверено автотестом 2026-08-21)
- Наблюдение: `API_REFERENCE.md` и backend-контракт допускают текст набора до 500
  символов, но textarea формы имеет `maxlength="250"` и обрезает остаток.
- Влияние: валидный по API текст невозможно ввести через пользовательский UI.
- Ожидание: привести UI к документированному лимиту 500 либо согласованно изменить
  контракт и документацию, если продуктовый лимит должен быть равен 250.
- Проверка фикса: textarea принимает 500 символов, тест проходит без xfail.

### UI-020 — Названия вариантов оформления профиля дублируются в accessibility tree

- Приоритет: P2
- Статус: Confirmed (2026-08-21)

  вложенного изображения, и как видимая подпись. Например, карточка «Вулкан» получает
  доступное имя `Вулкан Вулкан` вместо `Вулкан`.
- Влияние: screen reader дважды произносит одно название, а семантический locator по
  ожидаемому пользовательскому имени не находит кнопку. Тест временно ограничивает
  `button` по его видимому тексту.
- Ожидание: декоративное изображение внутри уже подписанной кнопки должно иметь пустой
  `alt`, либо сама кнопка должна получить единичный `aria-label`.

### UI-021 — Экипированный шлем не отображается на модели персонажа

- Тип: UI / functional
- Приоритет: P1
- Статус: Confirmed (2026-08-21)
- Предусловие: через `POST /api/inventory/equip` экипирован `eq_head_t1` в слот `head`;
  профиль возвращает предмет в `equipment.head`, слот UI заполнен, мощность равна 110 IP.
- Шаги: открыть инвентарь и оставить switch «Скрыть шлем» выключенным.
- Фактически: голова персонажа остаётся открытой; включение «Скрыть шлем» визуально модель
  также не меняет.
- Ожидается: при выключенной настройке экипированный шлем виден на модели, при включённой —
  скрыт. Regression-проверку не подменять проверкой заполненного equipment slot: это уже
  другое поведение и оно покрыто отдельно.

### UI-022 — Экран состава получает устаревшее состояние после изменения вклада

- Тип: UI / data freshness
- Приоритет: P1
- Статус: Confirmed (2026-08-21)
- Предусловие: создана гильдия из USER_1 и USER_2; USER_2 успешно внёс 1 серебро в
  технологию. Контрольный `GET /api/guild/members` вернул обоих участников и вклады
  `Тест 1: 0`, `Тест 2: 1`.
- Фактически: следующий запрос состава при открытии UI вернул/отобразил пустой roster:
  `Участников: 0`, общий вклад отсутствует, строки пользователей отсутствуют.
- Ожидается: `GET /api/guild/members` и экран состава сразу после успешного invest
  возвращают актуальных двух участников и общий вклад 1. Не исправлять тест повторным
  открытием экрана или искусственным ожиданием истечения cache.
- Автотест: сценарий сортировки реализован; `pytest.xfail` вызывается только после
  успешного ответа roster, если его payload расходится с уже подтверждённым API-состоянием.
  Поэтому посторонние 502/reset-ошибки не маскируются.

### API-006 — GET /api/guild возвращает 500 после reject и повторной заявки

- Тип: API / state consistency
- Приоритет: P1
- Статус: Confirmed (2026-08-21)
- Контекст: lifecycle дошёл до известного UI-011 после успешных create, первой заявки,
  reject и успешной повторной заявки. При обязательном cleanup запрос текущей гильдии
  `GET /api/guild` для тестового пользователя вернул `500` с телом
  `{"error":"Internal Server Error","code":"INTERNAL_ERROR"}`.
- Влияние: cleanup не может определить членство и безопасно распустить одноразовую
  гильдию; ожидаемый точечный `xfail` UI-011 корректно превращается в failure из-за
  ошибки cleanup.
- Ожидается: endpoint стабильно возвращает объект гильдии либо `[]`. Не подавлять ошибку
  cleanup и не повторять запрос автоматически.

### UI-023 — Активная кнопка изучения навыка молча игнорирует недостаток LP

- Тип: UI / validation / UX
- Приоритет: P1
- Статус: Confirmed (2026-08-21)
- Предусловие: API-setup оставляет 9 LP при цене кнопки `Учить (10 LP)`; профиль до
  открытия UI подтверждает остаток и текущее состояние навыка.
- Фактически: кнопка имеет enabled-состояние, но клик не отправляет
  `POST /api/skills/inject` в течение 30 секунд и не предоставляет пользователю результат
  серверной валидации.
- Ожидается: либо кнопка disabled при `learningPoints < price`, либо клик отправляет запрос,
  получает документированный 400 «Недостаточно очков обучения» и показывает ошибку.
  Предпочтительный контракт для текущего UI — disabled-кнопка.
- Автотест: точечный `pytest.xfail` выполняется только после успешного setup и обнаружения
  enabled-состояния; инфраструктурные ошибки не маскируются.

## Правила добавления findings

- Не записывать предположение как подтверждённый bug.
- Для воспроизводимого дефекта указывать экран, действие, фактический и ожидаемый

- Проблемы тестового стенда отделять от продуктовых дефектов.
- После исправления сохранять запись и менять статус на `Fixed` с версией/датой.
