# Escapism — автотесты

Pet-проект автоматизированного тестирования web-игры Escapism, запускаемой как
VK Mini App. Тесты воспроизводят пользовательские действия через UI, а API
используется для подготовки данных и проверки итогового бизнес-состояния.

Автотесты написаны на Python с использованием pytest и Playwright.

План развития regression-покрытия и порядок реализации находятся в
[`REGRESSION_ROADMAP.md`](REGRESSION_ROADMAP.md).
Найденные дефекты и предложения по улучшению ведутся в
[`QA_FINDINGS.md`](QA_FINDINGS.md).

## Технологии

- Python 3.14
- pytest 9
- Playwright
- pytest-playwright
- python-dotenv

## Покрытие тестами

Текущее smoke-покрытие:

### Инвентарь

- Экипировка предмета
- Снятие экипированного предмета

### Навыки

- Прокачка навыка до первого уровня
- Списание очков обучения (LP)

### Биржа

- Обмен золота на серебро с проверкой влияния на курс
- Обратный обмен полученного серебра и проверка балансов

### Почта

- Отправка письма с двумя предметами между тестовыми пользователями
- Чтение письма и получение вложений через UI
- Проверка списания и зачисления предметов через API

### Гильдия

- Создание гильдии и подача заявки вторым пользователем
- Принятие заявки, проверка состава и исключение участника
- Проверка состава через API и состояния второго пользователя через UI

### Личный склад

- Перенос нескольких единиц предмета из сумки на склад через UI
- Возврат предмета со склада в сумку через UI
- Проверка дельт и сохранности общего количества через API

### Расходники

- Употребление еды через UI
- Проверка списания предмета и увеличения сытости через API

Новые сценарии будут добавляться по мере развития функциональности приложения.

## Установка

### 1. Создать виртуальное окружение

```powershell
python -m venv .venv
```

Активировать:

```powershell
.venv\Scripts\Activate.ps1
```

### 2. Установить зависимости

```powershell
pip install -r requirements.txt
```

Установить Chromium для Playwright:

```powershell
playwright install chromium
```

### 3. Настроить переменные окружения

Создать файл `.env` на основе `.env.example`:

```env
BASE_URL=https://example.com/
API_URL=https://api.scripthub.ru/api/
VK_LAUNCH_PARAMS_USER_1=?vk_user_id=...
VK_LAUNCH_PARAMS_USER_2=?vk_user_id=...
```

`API_URL` должен заканчиваться символом `/`, потому что API-клиент использует
относительные пути эндпоинтов. VK launch params передаются полной query-строкой,
включая ведущий `?`.

Файл `.env` содержит данные авторизации тестовых пользователей и не должен попадать в Git.

## Запуск тестов

Запустить все тесты:

```powershell
pytest
```

Запустить только smoke-тесты:

```powershell
pytest -m smoke
```

Запустить только regression-тесты:

```powershell
pytest -m regression
```

Текущий полный набор содержит два ожидаемо падающих strict xfail:

- `UI-011` — после повторной подачи badge показывает одну заявку, но список
  заявок лидера остаётся пустым.
- `API-005` — reset удаляет уникальное письмо, хотя опубликованный контракт
  обещает не изменять mail.

Исправление любого дефекта приведёт к `XPASS(strict)` и потребует снять отметку
известного дефекта с соответствующего теста.

По умолчанию Chromium запускается в headless-режиме. Видимое окно браузера
открывается только с флагом `--headed`.

Тесты используют общую пару выделенных аккаунтов и изменяют их inventory,
валюту, почту и guild-состояние. Поэтому нельзя одновременно запускать несколько
pytest-процессов или использовать `pytest-xdist -n`: параллельные reset и cleanup
нарушат предусловия соседнего теста. Для параллельного запуска нужны отдельные
USER_1/USER_2 на каждый worker либо серверный test-data namespace.

Запустить тесты с отображением браузера:

```powershell
pytest -m smoke --headed
```

Запустить конкретный файл:

```powershell
pytest tests/test_inventory.py -v
```

Запустить тест навыков:

```powershell
pytest tests/test_skills.py
```

## Подход к тестированию

Основные принципы проекта:

- тестируемое действие выполняется через UI;
- предусловия по возможности создаются через API;
- итоговое бизнес-состояние проверяется через API;
- перед каждым тестом пользователь сбрасывается в известное состояние;
- каждый UI-тест получает отдельный `BrowserContext`;
- Page Object и дополнительные fixtures добавляются после появления повторяющегося кода.

API используется для:
- подготовки тестовых данных;
- сброса тестовых пользователей в начальное состояние;
- проверки состояния данных после действий через UI.

Эндпоинты отзыва launch params (`/api/v1/account/revoke` и
`/api/v1/account/sessions/revoke`) не автоматизированы на общих USER_1/USER_2:
они необратимо инвалидируют используемые suite-сессии. Для них нужны отдельные
одноразовые аккаунты или механизм выпуска новых launch params в CI.

Перед выполнением теста пользователь сбрасывается в заранее известное состояние через API. Это позволяет сделать тесты независимыми и воспроизводимыми.

Для сброса используется служебный endpoint `POST /api/v1/account/reset`. Он не входит
в публичный контракт из `API_REFERENCE.md` и предназначен для тестовой подготовки.

Account reset очищает inventory, equipment, skills, recipes, личный склад,
валюты, LP и прогресс персонажа. Публичный контракт заявляет, что guild и mail
не изменяются, но стенд фактически пересоздаёт почту (API-005). Поэтому mail-тесты
удаляют только созданные ими данные, а зависимость от reset ограничена setup.
Guild-тесты сохраняют явный cleanup. Ошибки cleanup не подавляются.

Данные авторизации VK хранятся в переменных окружения и не добавляются в репозиторий.

## Smoke-покрытие

Smoke-набор предназначен для проверки основного критичного функционала приложения.

Реализовано:

- Инвентарь — экипировка и снятие предмета
- Навыки — прокачка навыка «Меч» до первого уровня и списание LP
- Биржа — обмен золота на серебро и компенсирующий обратный обмен
- Почта — отправка и получение письма с предметами двумя пользователями
- Почта — обязательное подтверждение удаления с проверкой отмены и DELETE
- Гильдия — создание, вступление второго пользователя, принятие и исключение
- Гильдия — серверные запреты kick и управления технологиями для роли member
- Гильдия — переход в почту через доступную кнопку в header каталога
- Личный склад — перенос предмета из сумки на склад и обратно
- Настройки внешности — доступный switch видимости шлема с восстановлением состояния
- Инвентарь — API-driven проверка информации о желудке и закрытия модалки
- Инвентарь — мощность до/после API-экипировки, детализация, scroll и backdrop
- Профиль — смена титула из API-справочника с восстановлением исходного значения
- Профиль — параметризованная смена фона, рамки и аватара с проверкой запроса,
  итогового API-состояния и восстановлением исходных значений
- Расходники — употребление еды и проверка изменения сытости

Текущий smoke-набор завершён. Новые сценарии стоит добавлять только при появлении
нового критичного пользовательского пути. Проверки блокировки предметов,
кастомизации профиля, фильтров и альтернативных UI-действий относятся к
regression-покрытию.

## CI

Smoke-тесты запускаются в GitHub Actions на push и pull request. В настройках
репозитория нужно создать Actions secrets:

- `BASE_URL`
- `API_URL`
- `VK_LAUNCH_PARAMS_USER_1`
- `VK_LAUNCH_PARAMS_USER_2`

Workflow устанавливает Python 3.14 и Chromium, после чего запускает:

```text
pytest -m smoke --browser chromium
```

### Запуск разработчиком через GitHub

Владелец репозитория должен:

1. Добавить разработчика в collaborators с уровнем доступа `Write`.
2. В `Settings → Secrets and variables → Actions` создать repository secrets:
   `BASE_URL`, `API_URL`, `VK_LAUNCH_PARAMS_USER_1` и
   `VK_LAUNCH_PARAMS_USER_2`.
3. Не передавать разработчику файл `.env`: GitHub подставляет secrets только во
   время выполнения workflow и скрывает их значения в интерфейсе.

После получения доступа разработчик может открыть `Actions → Tests`, нажать
`Run workflow`, выбрать ветку и запустить smoke-набор. Для ручного запуска нужен
доступ `Write`; пользователь с read-only доступом может просматривать уже
запущенные проверки, но не запускать workflow вручную.

Прогоны выполняются последовательно, потому что используют общих тестовых
пользователей и изменяют общий exchange-пул. После завершения в разделе
`Artifacts` сохраняется HTML-отчёт, screenshots и Playwright traces для падений;
срок хранения — 14 дней.

## Известный технический долг

- Кнопка изучения навыка «Меч» временно выбирается как первая кнопка
  `Учить (10 LP)`.
- После повторной подачи заявки badge лидера показывает `Заявки (1)`, но список
  заявок может остаться пустым (UI-011). Тест не маскирует это reload/retry.
- API тестового стенда снова вернул `502` и несколько `500` в полном
  последовательном прогоне 2026-08-21; автоматические retry не используются.

Для кнопки конкретного навыка frontend должен предоставить стабильное доступное
имя или `data-testid` с идентификатором навыка.
